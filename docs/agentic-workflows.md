# GitHub Agentic Workflows

Three agentic workflows live in `.github/workflows/` as `.md` files. Each is a YAML frontmatter
block plus natural-language instructions, compiled by `gh aw` into a hardened `.lock.yml` that
GitHub Actions actually runs. **Both files are committed** — the `.md` is the source, the
`.lock.yml` is what executes, and they must stay in sync.

## The three

| Workflow | Trigger | Write capability | Point |
|---|---|---|---|
| `bicep-pr-reviewer.md` | `pull_request` | `add-comment` | Reviews changed Bicep against this repo's own instruction files |
| `daily-iac-report.md` | `schedule: daily` | `create-issue` | Reports PRs, failing runs, PSRule findings, pending deployments |
| `version-sync-fixer.md` | `issues: labeled` | `create-pull-request` | Fixes version drift — only ever by opening a PR |

`agentics-maintenance.yml` is generated by `gh aw` (it runs `permissions: {}` cleanup for
expiring safe outputs). Do not hand-edit it; it regenerates on `gh aw compile`.

## Why `safe-outputs` is the interesting part

An agentic workflow is **read-only by default**. It has no ability to write anything unless a
capability is declared under `safe-outputs:`, and it gets exactly the ones listed — nothing
more, no matter what the instructions say or what a prompt injection tries to talk it into.

Look at `version-sync-fixer` in that light. It is the only workflow here that changes code, and
its capability is `create-pull-request`, not push access. So its output lands where a human's
does: a branch, a pull request, the three required checks, a review. An agent that could push
would bypass all four, and no amount of careful prompting would put them back.

That is the shape worth taking away: **the guardrail is the absent capability, not the
instruction not to use it.**

Other protections `gh aw` applies on top:

- Write operations run in a separate job whose permissions the agent never holds.
- Secrets stay in downstream jobs, out of the agent's runtime.
- Proposed outputs are scanned before they are applied.
- The agent runs firewalled and network-restricted (`network: defaults`).
- Role-based control over who can trigger a workflow.

## Toolsets and permissions are coupled

The `tools.github.toolsets` list determines which permissions the workflow needs. Asking for
`[default]` pulls in issues *and* pull requests, and the compiler then warns that the
permissions do not cover it.

The tempting fix is to grant the permission. The better fix is usually to want less:

```yaml
# bicep-pr-reviewer: reads PRs and files, never issues
toolsets: [context, repos, pull_requests]

# version-sync-fixer: reads one issue and some files, never PRs
toolsets: [context, repos, issues]
```

Both compile with zero warnings and neither can read something it has no use for.

### …and the compiler only warns in one direction

The trap is the inverse case, and `daily-iac-report` walked straight into it.

It was written with `permissions: actions: read` and `security-events: read` — the right to
read workflow runs and code scanning alerts — but `toolsets: [default]`, which covers issues,
pull requests, commits, releases and contents, and **nothing else**. The agent had the
permission and no tool with which to use it.

`gh aw compile` reported **0 errors, 0 warnings**. It checks that your permissions cover your
toolsets; it does not check that your toolsets cover your prompt. Too few tools is not a
compile error, it is a silently smaller report.

What caught it was the workflow's own instruction to declare what it could not check:

> ### Not checked — tooling gap
> This session's available GitHub MCP tools only cover issues, pull requests, commits,
> releases, and repository contents. There is no tool exposed for listing GitHub Actions
> workflow runs or code scanning alerts. […] Flagging this as a monitoring gap.

gh-aw also raised a `missing_tool` safe output, which opened a second issue automatically.
Without either, the report would simply have said "0 workflow failures" — indistinguishable
from a healthy repository, forever.

The rule that survives: **`permissions` and `toolsets` are two separate grants, and you need
both.** Ask for the smallest toolset that covers what the prompt actually asks the agent to
do — then read the first real run to find out whether you guessed right.

## Working on them

```bash
gh extension install github/gh-aw

gh aw compile          # regenerate .lock.yml — required after ANY .md edit
gh aw lint             # actionlint over the generated workflows
gh aw run <name>       # execute one
gh aw logs <name>      # download and analyse run logs
gh aw audit <run-id>   # inspect a run in detail
```

If you edit a `.md` and do not recompile, the `.lock.yml` is what runs — meaning your change
silently does nothing. Commit both, always.

## Prerequisite before they will run

These are **authored and compiled but not yet runnable**. On a personal repository they need:

1. An active paid Copilot plan.
2. A repository secret `COPILOT_GITHUB_TOKEN` — a fine-grained personal access token:

   ```bash
   gh secret set COPILOT_GITHUB_TOKEN --repo mflorez-bag/agentic-ai-practice
   ```

On an organisation-owned repository you would instead add `copilot-requests: write` to
`permissions:` and enable the org policy "Allow use of Copilot CLI billed to the organization".
That difference — personal repo needs a token, org repo needs a policy — is the kind of thing
the exam asks about.

## Choosing a model — and the failure it causes

`gh aw` defaults to `claude-sonnet-4.6`. **That model is not available on every Copilot tier**,
and when it isn't, the run dies with:

```
[copilot-harness] attempt 1: model not supported — not retrying
(the requested model is unavailable for this subscription tier;
 specify a supported model in the workflow frontmatter)
```

To find out what your token can actually use, run any workflow once and read
`agent/sandbox/firewall/logs/api-proxy-logs/models.json` from the run artefacts. It lists the
models the server offered *your* subscription — which is a shorter list than the catalogue in
`activation/models.json`.

Set the model repository-wide rather than per workflow:

```bash
gh aw env get aw-env.yml
# set default_model_copilot: "gpt-4.1"
gh aw env update aw-env.yml --scope repo
```

Observed on this repo's Copilot seat, five runs:

| Model | Result |
|---|---|
| `claude-sonnet-4.6` (gh-aw default) | ✗ `model not supported` — not offered to this account at all |
| `claude-sonnet-5` @ 30-credit cap | ✗ HTTP 403 after 6 calls |
| `gpt-5.5` @ 30-credit cap | ✗ HTTP 403, same way |
| `gpt-4.1` @ 30-credit cap | ✓ completed — it is cheap enough to fit |
| `claude-sonnet-5` @ 150-credit cap | ✓ completed |

**Only the first row is an entitlement problem.** The rest were the per-run credit cap, and
diagnosing them as anything else cost an afternoon. The story is worth keeping because the
misdiagnosis is the interesting part.

### The cap is enforced as HTTP 403

`GH_AW_DEFAULT_MAX_AI_CREDITS` is enforced by gh-aw's own API proxy, which sits between the
Copilot CLI and GitHub. When a run exceeds it, the proxy rejects further requests with **HTTP
403** — and the harness classifies that as:

```
failureClass=authentication_failed
isCAPIQuotaExceededError=false   isInvocationCapExceeded=false
Authentication failed with provider at http://172.30.0.30:10002 (HTTP 403).
  Check your COPILOT_PROVIDER_API_KEY or COPILOT_PROVIDER_BEARER_TOKEN.
```

Every word of that points at credentials. Nothing mentions the budget. The `172.30.0.30`
address is the local proxy container, not GitHub — that is the tell.

**Read the numbers, not the label.** The truth is in the run artefacts at
`agent/sandbox/firewall/logs/api-proxy-logs/token-usage.jsonl`:

```
call 1   16.540 credits   running total  16.540   claude-sonnet-5   status 200
call 2    4.189                          20.729                     status 200
...
call 6    2.806                          30.331   ← crossed the cap
call 7        —                               —                     status 403
```

Six successful `status: 200` completions prove the model was entitled and working. An
entitlement failure would have been rejected on call 1.

### Budget accordingly

Cost varies enormously by model. Reviewing the same pull request:

| Model | Cost |
|---|---|
| `claude-sonnet-5` | ~16.5 credits on the first call alone, 30+ for a full review |
| `gpt-4.1` | ~3.25 credits billed for the whole review |

The first call is the expensive one — it writes the context cache (39K cache-write tokens
here). Later calls read from it cheaply.

So a cap tight enough for `gpt-4.1` silently breaks `claude-sonnet-5`. This repo now runs
`claude-sonnet-5` with 150 credits per run and 600 per day. Tune both against your own
allowance; if you switch to a cheaper model, lower them again rather than leaving headroom you
are not using.

## Agentic workflows vs. the cloud agent

Both run Copilot; they are not the same thing and are configured separately.

| | Cloud agent | Agentic workflow |
|---|---|---|
| Invoked by | assigning an issue or PR to Copilot | a workflow trigger |
| Instructions | `AGENTS.md`, `.github/instructions/`, `.github/agents/` | the workflow's own `.md` body |
| Environment | `copilot-setup-steps.yml` | the Actions runner |
| Tools | agent profile `tools:` + repo MCP settings | `tools:` in the workflow frontmatter |
| Writes | commits to a `copilot/*` branch, opens a PR | only what `safe-outputs:` declares |

Use the cloud agent for open-ended work someone asked for. Use an agentic workflow for a
recurring job with a narrow, declared output.
